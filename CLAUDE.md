# Joebros business app

Modular operations app for Joebros Contracting Services (general contracting, Kent and Sussex County, Delaware), built to grow into an ERP.

## How work is planned
- The build is split into one-session chunks (F1, F2, ... S1, O1, ...). The roadmap with each chunk's scope, "done when" line and dependencies lives in the project file `/mnt/project-files/erp-plan/joebros-build-roadmap.html` (the `PHASES` array).
- Build only the chunk asked for, on its own branch (`<chunk-id>-<short-name>`), and stop when its "done when" line holds.

## Stack
- React 19 + TypeScript + Vite, React Router. No UI framework; plain CSS. All colors, type sizes and spacing are tokens in `src/styles/tokens.css` (light, dark, and follow-device themes). Never hardcode a color.
- Database: Supabase Postgres. Schema is SQL in `supabase/migrations/` (new file per change, never edit an applied one), sample rows in `supabase/seed.sql` (`is_example = true`). This project does not expose new tables to the API automatically: every new table needs explicit `grant ... to authenticated` in its migration (see `20261128000000_api_grants.sql`), then RLS policies. Merging to main applies them via `.github/workflows/database.yml`. Tests run migrations in PGlite (`supabase/tests`). See `supabase/README.md`.
- Sign-in: Supabase Auth (F4). `src/core/auth` holds the provider, sign-in screens and an `AuthClient` interface (tests use `fakeAuth`). The role comes from `profiles.role`; RLS in the database is the real gate, the menu just mirrors it. Without `VITE_SUPABASE_PUBLISHABLE_KEY` the app runs in preview mode with a "Preview as" role picker and no data. See `.env.example`.
- Settings (F5): `src/core/settings` holds `SettingsProvider`/`useSettings()` (company profile, switched-off modules, dropdown lists via `choices("trade")`) behind a `SettingsBackend` interface; tests and preview mode use `memorySettings()`. Use `choices(...)` for lead source and trade dropdowns instead of hardcoding lists. Invites go through the `invite-user` edge function in `supabase/functions`.
- Tickets (F6): `src/core/tickets` holds the stage rules (`stages.ts`, mirroring `ticket_stage_transitions` and `role_can_edit_stage`), a `TicketsBackend` interface (`supabaseTickets`, `memoryTickets` for preview and tests) and `useTickets()`. `useCurrentUser()` (`src/core/currentUser.tsx`) gives screens the signed-in role and id. The Tickets module (`/tickets`, `/tickets/new`, `/tickets/:number`) is the shared ticket screen other modules link to. The timeline comes from `ticket_events`, written by database triggers.
- Import (F8): `src/modules/import` is an admin-only screen for a JSON or CSV export from the old single-page Joebros CRM. `src/core/import` parses it, plans creates against matches on normalized phone then email, and writes through `supabaseImport` (preview and tests use `memoryImport`). Imported rows are tagged `import_source = 'joebros-crm'`. Dry run writes nothing. The old CRM page is a Claude artifact and is not in this repo.
- Contact sync (C2): phone, email and address live only on `contacts`/`properties`; tickets join them, so edits show everywhere. Tickets edit them through `EditContact`/`EditProperty` in `src/modules/contacts/EditSheets.tsx`. The `contact_changes` table (trigger-written) is the change log, read via `ContactsBackend.changes()` and merged into timelines with `mergeTimeline`. In preview, `memoryTickets({ contacts })` reads customer details from `memoryContacts` the same way.
- Price book (S1): `src/core/pricebook` holds `price_items` types (kinds labor, material, adder, multiplier), `checkItem`/`normalizeItem` (mirroring the table checks), a `PriceBookBackend` (`supabasePriceBook`, `memoryPriceBook`), `usePriceBook()` and `PriceItemPicker` (search and pick active items, by kind and trade) for the estimate builder. Items are retired, never deleted; estimates should copy name, unit and numbers onto their lines. The Price book module (`/price-book`) is admin-editable and read-only for sales.
- Estimate math (S2): `src/core/estimate` holds `calculateEstimate(input)`, the one place estimate numbers are worked out (labor qty × rate, materials cost + markup, adders, multipliers on labor/materials/whole estimate, tax on chosen parts, rounding of the total to $0.01/$1/$5...). Pure functions, worked in whole cents so every part adds up exactly to the total; bad numbers are ignored and listed in `issues` instead of throwing. `lineFromItem` copies a price book item onto an estimate line. The builder (S3), customer document (S4) and invoices must use it rather than doing their own math.
- Estimate builder (S3): `estimates` (one per option on a ticket; the working draft: `lines` JSON in the `EstimateInput` shape, customer `notes`, `internal_notes`, `total`) and `estimate_versions` (numbered by a trigger, never updated; saving one sets the ticket's `estimated_value`). `src/core/estimate/store.ts` holds the types, `normalizeLines` and an `EstimatesBackend` (`supabaseEstimates`, `memoryEstimates`) behind `useEstimates()`. Screens are in the Sales module: `/sales` (list), `/sales/new?ticket=N` (moves a lead or site-visit ticket to Estimating), `/sales/estimates/:id` (builder: Time, Materials, Adders, Multipliers, Tax and rounding, Notes, Versions; the draft autosaves; the total comes only from `calculateEstimate`). Tickets show their estimates via `TicketEstimates`. S4 should render from a saved version.
- Calendar (S8): `src/core/calendar` holds the event model (`calendar_events`: kind, tentative/confirmed status, crew, palette color, ticket), a `CalendarBackend` (`supabaseCalendar`, `memoryCalendar`), `useCalendar()` and `TimeGrid`, the drag-to-create/move/resize grid. `TimeGrid` takes generic columns (one per day now; per crew and day for the O2 board via `eventsFor`). Event and crew colors are palette names mapped to `--ev-<name>` tokens. The Calendar module is `/calendar?view=day|week&date=YYYY-MM-DD`.
- Crews (O1): `src/core/crews` holds `crews` (name, palette color, skills = trade labels, work days 0=Sun..6, day start/end) and `technicians` (optional crew, optional linked login, skills), a `CrewsBackend` (`supabaseCrews`, `memoryCrews`), `useCrews()` (`colorOf(crewId)`, `crewById`), `CrewChip` (name with color dot: use it wherever a crew is named) and `ColorPicker`. Managed in Settings (admin; the database also lets operations edit). Bookings take their crew's color via `eventColor(e, colorOf(e.crewId))` unless they set their own. Crews and techs are retired (`active = false`), not deleted.
- Backups (F9): `.github/workflows/backup.yml` dumps the live database nightly (roles, schema, data via `supabase db dump --remote`), test-restores it into a throwaway `supabase db start` database with `scripts/backup/verify-restore.sh` (row counts per table), then keeps a 7z AES-256 archive (secret `BACKUP_PASSWORD`) as a 30-day run artifact. The repo is public: never upload an unencrypted dump or print rows in a log. Restore steps are in `supabase/README.md`.
- Planned: Supabase Storage, Resend email, Leaflet + OpenRouteService maps, hosting on Cloudflare Pages. Keep everything on free tiers unless the owner approves a cost.

## Conventions
- Each module lives in `src/modules/<id>/index.tsx` and exports a `ModuleDefinition` (see `src/core/modules.ts`). Register it in `src/modules/registry.ts`; menu and routes are generated from the registry.
- Build screens from the shared components in `src/ui` (Button, TextField/SelectField/TextAreaField with bubble notes, CheckChips, Section, Sheet, DataTable, Badge, InfoTip). The admin-only Style guide page (`/styleguide`) shows them all; add new shared components there too.
- Use `Section` with a `storageKey` for collapsible areas so open/closed is remembered.
- Pages use `ModulePage` from `src/core/ModulePage.tsx` for a consistent header.
- Must read well on a PC first (full sidebar, 16px base text) and work on phones (sidebar becomes a drawer below 900px).
- Never hardcode secrets. Supabase keys come from environment variables.

## Commands
- `npm run dev`: local dev server
- `npm test`: unit and component tests (Vitest)
- `npm run typecheck`, `npm run build`
